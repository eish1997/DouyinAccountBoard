## 1. 用途与目标

本手册用于AI Agent接到明确开发指令后，以“读取状态 → 选择任务 → 实现 → 验证 → 审查 → 记录 → 下一轮”的方式持续推进。每轮交付一个可核对的小结果，不停留在反复规划，也不以代码已经写完代替验收通过。

目标是落实配套上线计划：员工通过统一HTTPS网址，以独立账号访问同一后台和共享持久数据；管理员跨办公室管理，员工范围明确授权；核心查看、新增、编辑、导入导出和截图流程可复现验收；采集暂缓。复用现有网页、Python后端和`web_server.py`，不增加审批、绩效、经营报表、自动发布等功能。

本文规定执行方法，上线计划规定产品范围、技术要求、验收和上线阻断条件。未来阅读本文不等于获得修改、运行、安装、购买、部署或使用客户数据的授权。本次编写文档也不启动任何自动循环、计划任务或后台Agent。

## 2. 指令与授权边界

### 2.1 每次启动先核对

1. 阅读当前会话中的用户指令和适用的上级约束。
2. 查找项目目录、父目录以及目标子目录内适用的`AGENTS.md`等说明；不存在就如实记录，不猜测。
3. 阅读上线计划、本文和已有开发状态记录。代码事实与文档矛盾时先复核，记录差异；不能自行放宽用户要求。
4. 确认本次允许的操作、工作目录和数据环境。继承仍有效的授权，不为已授权的普通修复反复询问；也不能把“继续”“按计划”理解成自动授权此前明确禁止的真实数据库操作。

本地执行默认遵守以下边界；如果用户另有明确授权，记录授权对象和范围后按新边界执行。

| 操作 | 执行规则 |
| --- | --- |
| 阅读源码和文档、检查依赖声明 | 可在审查或开发范围内进行；不读取业务记录来生成报告 |
| 修改业务代码 | 只有明确启动开发后执行；本手册的存在不构成授权 |
| 测试及本地服务 | 开发启动后仍须满足隔离要求；不能让默认入口连接真实库 |
| 安装依赖、拉取容器或改变环境 | 核对会话授权与现有限制；只在获准的隔离环境执行，不能修改全局运行时或假定网络权限已授予 |
| 客户数据库、真实备份、种子、浏览器profile、登录态 | 不用于试验、失败注入、迁移演练或负载测试；不能复制到新环境作捷径 |
| 云资源、费用、部署、上传客户资料、正式迁移、切换 | 逐项遵循已有明确授权；未获授权只准备可审查的配置、工具和操作步骤 |
| 凭据及业务信息输出 | 不输出密码、密码哈希、令牌、Cookie、连接串秘密或真实客户记录；日志和证据先脱敏 |
| 新业务功能、删除历史、恢复采集 | 不属于首版默认范围，不能自主加入或执行 |
| 其他Agent、外部消息、自动任务 | 遵循当前工具及用户授权；不能把本手册当作创建子Agent、给其他会话发消息或设置自动运行的授权 |

需要确认时说明具体阻塞项及原因，并继续其他已经授权、没有依赖的工作。不要提出泛化的“是否继续”。平台选型、费用或客户操作确实阻塞时，准备好对比、推荐及可审查步骤后再请求决定。

## 3. 环境与真实数据隔离

在T01建立以下保护，再运行可能写数据的命令：

- 测试根目录必须由执行配置明确给出，使用项目内新建的专用测试目录或获准的临时目录。测试库必须由合成生成器创建，并带环境标识；目录名称包含`test`不算充分证明。
- 校验路径解析后的绝对位置，拒绝客户库、正式数据目录、备份目录、profile及指向这些位置的链接或目录联接。不能只检查字符串前缀。
- 读取启动代码与配置加载逻辑，确认缺少测试参数会拒绝启动，而非回退到`data/board.db`或客户种子。
- 测试数据库连接必须核对主机、数据库名和环境标识，拒绝生产目标；只使用合成账号。不要在工具输出中打印完整连接串。
- 测试服务只监听本机或获准的隔离网络，使用独立端口、会话和功能配置。采集保持禁用，不启动浏览器登录或Worker。
- 执行备份、恢复、迁移、导入和清理前，再次确认源与目标；演练对象均为合成或另行批准脱敏的数据。
- 清理仅限当前任务创建且已确认位于测试根下的资源；不可因名称匹配而递归清理未知目录。保留必要证据，避免后台进程或端口残留。

不能证明隔离安全时，不运行项目以“试试看”。先完成隔离入口或将依赖标为阻塞；静态阅读仍可继续。现有测试也须先读其初始化和路径逻辑，不能因为名为测试就默认安全。

## 4. 状态与证据组织

开发启动后再创建以下文件；本文中的路径是建议的状态结构，不表示文件已经存在。

```text
docs/agent-dev/
  状态.md                  # 当前阶段、授权、任务状态、下轮入口
  决策记录.md              # 选型与契约变更，保留历史决定及原因
  验收矩阵.md              # A01—A21及负载/灾备逐项证据
  循环记录.md              # 每轮追加摘要，不覆盖历史
  evidence/
    loop-0001/             # 经脱敏的命令、环境、输出摘要与报告
```

合成数据库、图片和运行缓存放在专用测试根，不写进文档证据目录；源码仓库只保留生成器、测试配置和适量脱敏报告。使用Git前先确认仓库存在及适用规则；没有Git就用有边界的文件清单和差异记录，不自动初始化仓库。不要覆盖用户已有修改，不执行破坏性重置。是否提交或推送遵循会话与仓库规则，不能为了“每轮完成”强行提交别人的改动。

### 4.1 状态分为执行状态与证据状态

| 维度 | 状态 | 含义 |
| --- | --- | --- |
| 执行 | 待开始 | 尚未开始该项 |
| 执行 | 进行中 | 当前有一个明确的小步在实施 |
| 执行 | 阻塞 | 缺少明确依赖、授权、环境或决定，记录解除条件 |
| 执行 | 待验收 | 实现完成，但必要证据未齐 |
| 执行 | 已完成 | 该任务全部必需验收通过，证据对应当前版本 |
| 证据 | 未验证 | 只有设计或代码，无运行证据 |
| 证据 | 本地通过 | 指定隔离环境下指定用例通过 |
| 证据 | 平台待验证 | 本地结果存在，真实平台行为尚未验证 |
| 证据 | 验收通过 | 规定环境及全部必要场景通过 |
| 证据 | 失败/已过期 | 用例失败，或相关变更使旧证据不再能支持结论 |

“本地通过”不等于“可上线”。混合本地和平台要求的任务可以有本地子项完成、平台子项待验收，但整体不得提前标为已完成。记录中的“阻塞”仅表示项目任务状态，不自动调用或更改任何工具的goal状态；工具自身的状态规则仍须遵守。

此表是工作导航，不能代替上线计划中每项的完整验收、依赖和回滚要求。

任务可拆成本地实现、局部验证和平台验收三个子项。依赖应引用所需的具体交付物，例如T02本地开发依赖T05数据库适配及锁协议的本地通过证据，不必等待尚未授权的云端发布；但T05的平台子项继续保持待验收，T12不得放行。接口尚未确定或必要正确性验证失败时，不能以“先用模拟结果”绕过依赖。

选任务优先级：

1. 先处理当前变更引入的失败、越权、数据完整性风险或阻断后续的契约缺口。
2. 再选依赖已满足且授权明确的最早未完成子项。
3. 若被平台或授权阻塞，记录原因，选择其他独立的本地子项；不要在未定数据库产品上实现一整套猜测方案。
4. 若只剩外部阻塞，没有可安全推进的工作，则保存检查点并报告，不重复执行同一失败命令。

## 6. 单轮开发Loop

### 步骤1：恢复上下文

读取状态、最后一轮记录和本轮关联的任务。检查源码是否变化、上轮测试是否仍在运行、计划版本是否更新。恢复时从检查点继续，不重复跑已完成的迁移或初始化。上轮是否执行成功不明时，先读状态和证据确认，不能盲目重放写操作。

### 步骤2：定义本轮小目标

一轮只选择一个可验证的行为变化或一个清晰的失败修复，通常限定一个主模块及必要调用方。写明：

- 对应任务与验收编号。
- 当前问题、预期行为、涉及路径和不在本轮范围内的内容。
- 需要满足的依赖与本轮验收方法。
- 回滚边界，以及是否触及结构变更或已有数据。

例：T03的一轮目标可以是“员工只改允许字段时使用一个请求，最后字段校验失败则全部不保存”，而不是“完成账号模块全部重构”。

### 步骤3：确认复现和最小方案

先阅读相关调用链及已有测试。对涉及权限、事务、并发、幂等、恢复的变化，建立能暴露问题的有意义用例或可重复故障场景；对简单文案和低风险文档修改不强制新增测试。

可以先运行受影响的安全基线，记录已有失败。不要把环境失败当业务缺陷，也不能用“原来就失败”掩盖本轮涉及的核心风险。没有运行条件时标为静态分析，不写“测试通过”。

### 步骤4：实施最小变更

沿用现有模块组织，只改完成本轮目标所需部分。新增接口必须同时处理鉴权、输入校验、事务、冲突、异常及客户端反馈。不得以删除失败断言、跳过用例、取消版本保护、扩大员工权限、吞掉异常或关闭功能来换取绿色结果。

结构变更提供受控迁移和版本检查，不能让每个服务实例自动迁移；本轮只在隔离库应用。遇到依赖选型变化，先更新决策记录并说明受影响任务，不能静默改目标。

### 步骤5：验证行为

按“相关单元/服务测试 → 受影响接口集成 → 必要浏览器流程”的顺序验证。只有本轮改变了跨模块行为或出现新风险，才扩大回归范围；不要无理由反复执行完整长时压测。

记录实际使用的命令、工作目录、代码版本、非秘密配置名、合成数据种子、开始结束时间、退出码、用例统计和失败摘要。不存在的测试命令不得写成已执行；从仓库当前文件确定命令，不假定项目使用某个测试框架或脚本。

网络中断等故障注入只作用于测试资源。并发测试必须有可控制的执行顺序或同步屏障；两个普通请求都返回成功不能证明没有竞态。

### 步骤6：检查差异与安全边界

审查本轮全部差异及测试结果，至少核对：

- 是否覆盖所有相关入口，包括旧接口、批量、导入、图片、历史和导出。
- 是否出现扩大权限、部分保存、重复记录、旧值覆盖或审计归属错误。
- 是否误改客户路径、默认配置、秘密、生成物或用户原有修改。
- 异常及重启是否仍能保持维护、采集停用和持久数据安全。
- 接口变化是否同时更新了客户端，是否有陈旧请求或旧实例兼容问题。

不涉及的项可注明原因。对相同差异进行独立复读即可，不强制每轮启动其他Agent。若用户明确授权多Agent协作，按第10节执行。

### 步骤7：保存结果与检查点

通过时将本轮证据关联到任务和验收矩阵，追加循环记录并更新下一轮入口。失败时保存失败事实和下一种诊断方向，不伪造完成状态。新改动影响旧验收时将对应证据标为已过期，保留原报告供追踪。

每轮摘要模板：

```markdown
## loop-0001
- 目标：Txx / Axx；本轮行为变化
- 起始版本与结束差异：
- 修改文件和原因：
- 执行环境与合成数据：
- 实际命令、退出码、证据路径：
- 预期结果 / 实际结果：
- 自审发现及处理：
- 任务状态 / 证据状态：
- 风险或阻塞，所需决定：
- 回滚方式：
- 下一轮唯一入口：
```

### 步骤8：决定继续或退出

只要存在授权明确、依赖满足且有意义的下一步，就进入下一轮，无需每次请求“继续”。按运行平台要求发送简短进度，聚焦完成了什么、证据如何、当前阻塞是什么。

用户要求停止或暂停时，停止派发新工作，安全收尾当前操作并保存检查点；不要再开新一轮。运行平台的时间、上下文或工具限制到达时，完整保存状态并报告实际完成度，不声称任务全部完成，也不自行创建后台自动任务。

## 7. 循环控制伪代码

以下描述行为，不是可直接执行的脚本，也不自动创建长期运行目标。

```text
读取会话授权、项目说明、上线计划、状态和证据
核实工作区与测试隔离
如果本次没有开发授权：仅完成被请求的文档/审查工作，结束

循环：
    接收用户新指令；若暂停/停止，安全保存并结束
    核对现有状态与代码版本，恢复上轮检查点
    选择一个依赖满足且授权明确的最小子项
    若无可执行子项：
        若全部必要验收已通过：形成完成报告，结束
        否则汇总阻塞与解除条件，保存检查点，结束
    定义验收、修改边界、回滚路径
    复现/建立必要的验证场景
    实施最小变更
    执行对应验证并审查差异
    若失败：记录原因，选择新的诊断方向
    若通过：保存证据，按实际验证环境更新状态
    检查用户指令、运行限制及连续失败情况
    保存循环记录与下一步，然后继续
```

连续两轮对同一问题没有新增证据时，停止重复修补，转为定位根因：检查调用链、环境、测试假设或寻求必要决定。不要自动放宽验收；也不要因这一子项阻塞就停止所有可独立推进的工作。任何更高优先级的工具预算或停止规则优先于本段。

## 8. 本项目不可破坏的规则

### 8.1 权限与新增

管理员跨办公室，员工同时满足办公室范围和操作权限。默认无范围即无业务访问。列表过滤之外，所有单条、关联、图片、历史、导出、导入和批量入口都要服务端校验。新增资料必须有明确办公室归属，普通员工不能将未归属数据隐式开放。

撤权和写入遵循上线计划规定的事务先后关系；不能仅复用进入请求时读到的actor。只读用户的写接口也必须直接验收。

### 8.2 保存与重复请求

账号一次保存是单事务、按字段授权的补丁；字段失败不能部分成功。数据库迁移后要保留版本比较与写入不可分割的语义，并正确记录本事务审计。

非幂等动作绑定原请求ID、操作者、内容摘要和恢复代次。重复请求仍查当前权限。响应丢失只能查询原请求状态或按同一协议恢复，不自动生成新ID重试，不将旧代次请求当新操作。

### 8.3 恢复与采集

业务恢复和完整灾备分别验收。业务恢复不回滚当前人员授权、维护状态和恢复代次；旧页面、旧预览、旧请求及旧执行令牌不能复活。维护必须关闭新写准入并排空在途事务，失败保持维护。

采集新任务、领取、控制、心跳和结果入口全部隔离；原数据和可审查任务记录保留。测试不得通过启动真实浏览器或使用真实登录态验证停用功能。

### 8.4 平台与数据

CloudBase实例临时磁盘不能作为正式数据源。部署默认维护停写并阻止旧实例写入；正常副本数为1不等于发布期间无并发。数据库选型尚未形成决策时，不擅自购买或创建资源。

备份不以同机副本冒充独立灾备。恢复点1小时、核心恢复4小时，以及50用户稳态/75用户峰值等目标以实际演练和上线计划参数验收；不能用模拟接口结果代替平台证据。

## 9. 完成定义与停止条件

| 交付级别 | 可以声称的结果 | 不可以声称的结果 |
| --- | --- | --- |
| 单轮完成 | 一个小目标实现且列明验证结果 | 整个任务或项目自动通过 |
| 本地开发完成 | 本地必需子项通过，平台待验证列表明确 | 已部署、已能正式上线 |
| 平台验收完成 | 获准环境中必要平台用例通过 | 已取得客户数据上传或生产切换授权 |
| 发布准备完成 | 清单、证据、风险和回滚齐备，无未解决上线阻断 | 已完成生产切换 |
| 正式上线完成 | 仅在另获授权并实际执行、核对后使用此表述 | 将计划或准备工作当作实际上线 |

以下情况停止相关写操作，保存状态并报告：

- 发现目标可能是真实库、操作会泄露秘密或越过授权范围。
- 当前修改出现数据丢失、越权或无法保证回滚，且继续操作会扩大影响。
- 缺少数据库选型、实际代理信息、资源授权等不可推断的依赖。
- 必须改变已确认功能范围、降低验收目标或删除数据才能继续。
- 用户要求停止，或运行环境不允许继续。

处理方式是缩小影响、保全现状和证据，不擅自恢复真实备份。先检查是否存在其他可安全推进的任务；如果没有，再结束本轮并给出精确阻塞说明。

## 10. 多Agent协作（仅在明确授权时）

多个Agent共享目标时，由一个协调者维护主状态和验收矩阵；每个执行者领取明确的文件范围、任务子项和测试资源，不能并发改同一份状态或执行同一结构迁移。

- 权限、数据库、恢复和幂等共享契约先由T00固定，再拆任务；不能让每个Agent自行发明接口。
- 分配独立合成数据库、目录和端口，记录资源归属。多个测试进程不得误用同一个SQLite文件或恢复目标。
- 交付必须包含差异、实际测试证据、未完成项和集成要求；“已完成”消息不是验收凭据。
- 协调者合并后检查差异并执行相关集成验证；子Agent测试通过不代表合并后通过。
- 子Agent失败或退出时，先核对其工作区和运行资源再接手，避免重复执行。
- 如使用独立工作树，遵守仓库和会话规定；不要假定改动会自动同步，也不自动清理他人的工作树。

## 13. 每次交付给用户的简短报告

结束一个阶段或因阻塞结束时，用以下格式汇报，不要求用户阅读全部日志才能理解结果：

```text
本次完成：任务/子项，以及具体行为变化。
验证结果：实际执行的测试范围、通过/失败、证据位置。
未验证：平台、性能、恢复或其他尚缺证据的项目。
剩余风险/阻塞：原因、影响、解除条件。
下一步：下一轮从哪个子项或失败场景开始。
操作边界：本次实际涉及的环境；若有任何偏离授权立即说明。
```

持续开发的衡量标准是未完成项逐步减少、证据逐步完整、风险逐步明确。不要以循环次数、修改文件数或不断更新计划替代可验收的功能进展。
