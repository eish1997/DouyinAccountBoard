## C02 稳定办公室范围

沿用计划：owner和admin跨办公室访问，只有owner分配人员授权。employee/viewer必须同时满足办公室范围与原操作项权限；新员工、未显式分配的历史员工默认无范围。

offices使用不可变文本id、唯一name及active(0/1)，不从编号前缀/office_group推断。停用办公室不删除身份或资料。用户授权表user_office_grants以(user_id,office_id)为主键，外键分别引用auth_users/offices。auth_users.authorization_version为正bigint，修改角色、操作项、启用状态、办公室授权及密码时增加，撤销该用户全部会话。负责人停用员工后，旧会话再保存返回401且不改资料，该账号不能再登录。负责人重置他人密码后，旧会话再保存返回401且不改资料，旧密码不能登录，新密码可以登录；保存结果不含密码。人员保存不能停用、改角色或重置总管理员密码：这三项都返回403，角色、启用状态、姓名和密码摘要不变，原会话仍可使用，原密码仍可登录。只读人员被授予办公室后可以看见该办公室的账号，当天发布仍返回403且不写发布记录。人员管理不得给admin新增owner授权权力。

账号和电脑各属最多一个办公室：account_offices(account_id主键,office_id)、computer_offices(computer_id主键,office_id)。手机卡和手机设备可共用：phone_card_offices(card_id,office_id)、phone_device_offices(device_id,office_id)复合主键。各实体键与办公室均有外键。没有映射就是待核对，仅owner/admin可见，不自动对员工开放。

员工读取共用卡/设备需至少一个已授权的有效办公室与其映射相交；关联账号、姓名和数量只取该员工可读的账号。修改共用实体本身要求覆盖该实体全部办公室，并满足原操作权限；否则403，不让单办公室用户改变其他办公室共同使用的资料。管理员可访问待核对区；操作项仍独立校验。

新增API：账号传office_id，卡/设备传office_ids非空去重数组。普通员工不得省略或传空；单办公室由界面预填，服务端仍验证显式值。管理员可明确选择待核对区（null/空数组）。多个可选办公室必须显式选择，不按关联设备或当前筛选推断。改变归属检查旧范围与新范围；关系变更检查每个关联实体，但不隐式改写其归属。

读API返回受限offices及实体office_ids；/api/auth/me增加authorization_version和该用户office_ids（管理员用scope_mode=all明确表达）。总管理员的人员保存可提交office_ids；缺省更新保留旧范围，新人默认空。未知/停用办公室拒绝授予。

图片依据当前账号归属检查；人员无范围时列表/图片/历史/导出均不泄露。历史新增scope_offices文本保存该次变动涉及的旧、新及关联办公室并集；缺失/不完整历史范围仅管理员可见。员工查看历史还需当前实体可见，且事件范围全部在当前授权内。历史字段不引用当前offices外键，以保留恢复点之外的历史稳定ID。

实体版本必须包含office_ids，归属变更会改变版本。批量混入越界或不存在对象整批拒绝。事务内重读会话、当前权限、授权版本和当前范围；不得使用排队前actor。字段限制继续复用既有authorize函数，范围不能替代字段授权。同一账号并发补丁仍只有一方返回200、另一方409。失败方不新增该账号历史，审计只记成功方当前姓名。两人同时改同一账号的登录手机时仍只有一方返回200。失败方的目标设备版本和历史保持不变，原手机版本只随成功方变化一次。两人同时关联同一空发布格子时仍只有一方返回200。失败方的账号不出现在该批次，格子版本和历史只随成功方变化一次。

业务恢复包含offices及4种实体映射；当前user_office_grants和auth_users.authorization_version不回滚。恢复点缺少当前授权引用的办公室时保持维护，管理员核对；历史scope_offices随operations_history一并保留。

待核对资料和电脑归属由owner通过独立范围管理入口分配，不要求改写业务字段。GET /api/auth/entity-scopes按类型分页（100条）提供当前映射及scope_version；POST /api/auth/entity-scope必须携带expected_scope，旧版本409，单归属对象多选400。与人员授权一样先取得写准入，再检查当前owner身份；完整前后映射写入仅owner可查看的审计。该入口不授予普通管理员人员管理能力，也不自动建立任何映射。

## C03 保存幂等

idempotency_records字段：上述复合主键；action text、request_sha256 text、state(pending/succeeded/failed)、result_status integer、result_json text、created_at/completed_at bigint。结果不得保存密码、会话或图片原文。结果详情保留30天：同一内容在期限内回放正文；超过期限则清空正文并返回409 RESULT_EXPIRED，不重新执行。去重墓碑保留至代次关闭，超期后换内容仍拒绝。处理中的请求不因保留期被清空。查询须重新检查当前身份/权限/范围，不向失权用户返回旧结果。

## C04 维护关闭与排空

现有runtime_control(mode,writer_epoch,restore_generation)及行锁继续作为写事务准入。T06增加独立runtime_admission(id=1,closed boolean,request_id text,actor_id bigint,reason text,requested_at bigint)。先短事务提交closed=true，再等待runtime_control排空；业务写得到控制锁后也必须读最新admission，closed即拒绝。因此排空超时仍保持关闭，不能因控制锁等待失败退回可写。

关闭意图的短事务不持有admission锁等待runtime_control，避免倒序死锁。排空后将control置maintenance，再执行恢复/迁移。恢复失败保持closed和maintenance；开放需受控检查后在控制锁下更新control与admission，不自动开放。当前仅control围栏已测试，admission关闭意图与超时流程未实现，不算完整维护验收。

## C05 锁顺序与恢复

正常写/撤权：runtime_control → 当前人员授权 → 排序的关联实体/版本 → 幂等行；预约pending也是控制锁下的短事务。维护关闭意图独立短事务，不与排空合并持锁。单控制锁的性能尚需T11固定负载验证，不能仅凭本地竞态通过承诺50/75人达标。

业务恢复遵守restore-contract-v1.json：显式清单和指纹一致，不回滚人员授权/控制/代次/去重墓碑；任务历史保留但令牌失效。灾备另走完整应用schema/文件隔离还原、撤会话及新代次，不用平台其他数据库产品的备份说明替代PG证据。
